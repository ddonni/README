# 과제 8 제출물 — 내 소개 페이지에 패스키 달기

> **개인정보·비밀값 (T08-C12)**
> - 비공개 자리에 넣은 내용은 과제용으로 **만들어 넣은 짧은 메모**입니다. 실제 연락처·주소·신분증 번호 같은 **개인정보는 어디에도 없습니다.**
> - "지원하려는 곳"의 회사명(삼성, 데브시스터즈)은 누구나 아는 공개된 회사 이름이며 개인정보가 아닙니다.
> - 계정 이름은 실명이 아닌 "학원", "폰"입니다.
> - Supabase Secret key와 세션 쿠키 값은 제출물 어디에도 없습니다. 캡처에 찍힌 세션 쿠키는 가렸고, 해당 세션은 로그아웃으로 서버에서 지웠습니다.

## 인증 구현 설명서

### ① 무엇으로 붙였나
- **라이브러리 + 직접 구현** 조합입니다. 인증 서비스(Supabase Auth, Auth0 등)는 쓰지 않았습니다.
- **패스키 검증**: SimpleWebAuthn 라이브러리
  - 서버: `@simplewebauthn/server` 13.3
  - 브라우저: `@simplewebauthn/browser` 13.3 (파일을 `me/vendor/`에 직접 넣음)
- **세션**: 직접 구현했습니다.
  - 로그인에 성공하면 랜덤 토큰을 `__Host-sid` 쿠키(`HttpOnly; Secure; SameSite=Strict`, 8시간)로 줍니다.
  - DB(`me_sessions`)에는 토큰 원문이 아니라 SHA-256 해시만 저장합니다.
- **저장소**: Supabase(Postgres) 테이블 5개 — `me_users`, `me_passkeys`, `me_challenges`, `me_sessions`, `me_notes`
  - 모두 RLS를 켜고 정책은 두지 않았습니다. 그래서 서버의 Secret key로만 접근할 수 있습니다.
- **서버**: Vercel 서버리스 함수(`api/*.js`)

### ② 왜 그걸 골랐나
- **라이브러리에 맡긴 부분**: 서명 검증, CBOR·COSE 공개키 해석, origin·RP ID 확인입니다. 직접 짜면 틀리기 쉬운데, 틀려도 겉으로 드러나지 않습니다.
- **직접 쓴 부분**: 언제 질문을 만들고 언제 지우는지, 누가 등록·삭제할 수 있는지, 어느 계정의 자료를 돌려줄지입니다. 이 흐름이 코드에 그대로 보이게 하려고 직접 썼습니다.
- **인증 서비스를 쓰지 않은 이유**: 이 흐름이 서비스 안에 숨어 버립니다. 그러면 "공개키만 저장된다", "질문은 한 번만 쓴다"를 내 기록으로 보여 주기 어렵습니다.
- **Vercel + Supabase를 고른 이유**: 소개 페이지가 이미 Vercel에 있었고, 7번 과제에서 Supabase와 세션 쿠키를 써 봤습니다.

### ③ 어디를 어떻게 고쳤나
1번 소개 페이지의 공개 내용은 그대로 두었습니다. `index.html`에는 맨 아래 경계 상자 하나만 더했고, 나머지는 모두 새로 만든 파일입니다.

| 흐름 | 지나는 곳 |
|---|---|
| **등록** | 화면 `me/index.html`의 `register()`<br>→ `POST /api/register/options` (`api/register/options.js`): 질문을 만들고 `lib/auth.js`의 `rememberChallenge`로 DB에 5분 보관<br>→ 기기가 열쇠 한 쌍을 만듦<br>→ `POST /api/register/verify` (`api/register/verify.js`): `consumeChallenge`로 질문을 꺼내며 삭제 → `verifyRegistrationResponse` → `me_passkeys`에 공개키 저장 |
| **로그인** | 화면 `login()`<br>→ `POST /api/login/options` (`api/login/options.js`): 매번 새 질문<br>→ 기기가 개인키로 서명<br>→ `POST /api/login/verify` (`api/login/verify.js`): 질문을 꺼내며 삭제 → 패스키 ID로 공개키 찾기(없으면 401) → `verifyAuthenticationResponse` → 서명 횟수 갱신 → `lib/auth.js`의 `startSession` |
| **로그아웃** | `POST /api/logout` (`api/logout.js`) → `lib/auth.js`의 `endSession`: DB의 세션 줄을 지우고 쿠키를 비움 |
| **비공개 자료 조회** | 화면 `loadOpen()` → `GET /api/private` (`api/private.js`): `requireSession`으로 세션 확인(없으면 401) → 계정은 `session.user_id`에서만 정함 → `lib/store.js`의 `listNotes(userId)` / `getNote(id, userId)` |
| 패스키 목록·삭제 | `GET/DELETE /api/passkeys` (`api/passkeys.js`): 내 패스키만 다루고, 마지막 하나는 409로 막음 |

**남의 자료를 거절하는 소스 위치 (T08-C41)**
- `api/private.js`: 주소나 본문에 적힌 계정 값(`account`, `user`, `user_id` 등)은 무시하고 `session.user_id`만 씁니다.
- `lib/store.js`의 `getNote`, `deleteNote`, `deletePasskey`: 모든 조회·삭제에 `user_id` 조건이 붙어 있어서, 남의 번호를 주면 0건이 되고 404로 응답합니다.
- `api/passkeys.js`: 지우려는 패스키가 내 목록에 있는지 먼저 확인합니다.
- 403 대신 404를 쓴 이유: 403이면 "그 번호의 자료가 있긴 하다"는 사실이 새기 때문에, 남의 것과 없는 것을 같은 응답으로 돌려줍니다.

### ⑤ AI와 나
- **AI에게 맡긴 일**
  - 패스키 등록·로그인·로그아웃·비공개 조회 API, 비공개 화면, Supabase 테이블 SQL 작성
  - 로컬 자동 검증 스크립트와 기록 작성, 커밋·푸시
- **내가 직접 판단한 일**
  - 실제 기기로 계정과 패스키를 만들고 검증 순서를 정했습니다.
  - 데스크톱에서 계정이 꼬였을 때 계정을 지우고 처음부터 다시 만들었습니다.
  - 블루투스가 없는 데스크톱과 아이폰 조합에서 두 번째 패스키를 어디에 둘지 정했습니다. 구글 비밀번호 관리자와 Windows Hello, 서로 다른 두 저장소를 골랐습니다.
  - "지원하려는 곳"의 실제 회사명을 가상 이름으로 바꾸지 않고, 개인정보가 아니라고 문구를 바로잡기로 했습니다.
- **AI 제안을 따르지 않은 일**
  - 두 번째 패스키를 만들 때 AI는 크롬 개발자도구의 가상 인증기나 Bitwarden 확장을 쓰자고 했습니다.
  - 가상 인증기는 시험용이라 실제 백업이 되지 못하고, 확장은 따로 설치가 필요했습니다. 그래서 따르지 않았습니다.
  - 대신 크롬의 구글 비밀번호 관리자를 직접 찾아 실제 저장소 두 곳에 등록했습니다.

### ⑥ 아직 못 막은 것
1. **두 패스키가 결국 한 PC에서 만들어짐**
   - 블루투스가 없어서 아이폰을 두 번째 열쇠로 붙이지 못했습니다.
   - 구글 비밀번호 관리자 패스키는 구글 계정으로 동기화되므로, PC를 잃어도 다른 PC의 크롬에서 쓸 수 있습니다.
   - 하지만 구글 계정까지 잃으면 복구할 길이 없습니다.
2. **패스키를 모두 잃으면 복구할 길이 없음**
   - 마지막 패스키 삭제는 막았지만, 복구 메일·백업 코드가 없습니다.
   - 열쇠를 다 잃으면 Supabase에서 DB를 직접 고쳐야 합니다.
3. **질문 요청 횟수 제한이 없음**
   - `POST /api/login/options`를 반복해서 부르면 `me_challenges`에 5분짜리 줄이 계속 쌓입니다.
   - 요청 횟수 제한(rate limit)이 없어서 DB를 채우는 공격을 막지 못합니다.
4. **다른 기기의 세션을 끊는 버튼이 없음**
   - 로그인된 기기를 잃어버리면 최대 8시간 동안 세션이 살아 있습니다.
   - 끊는 방법은 그 패스키를 지우는 것뿐입니다. 지우면 그 패스키로 연 세션도 함께 삭제됩니다.
5. **계정 자리가 잠깐 열려 있었음**
   - 계정은 최대 2개이고, 지금은 다 차서 새 계정 등록이 403입니다.
   - 하지만 배포 직후나 계정을 지운 직후에는 `/me/` 주소를 아는 누구나 먼저 계정을 만들 수 있었습니다. 초대 코드 같은 확인이 없습니다.
6. **동기화 패스키에서는 복제 감지가 안 됨**
   - 서명 횟수가 줄면 거절하는 확인은 기기 전용 패스키에서만 작동합니다. 로컬 시험에서 실제로 "counter value 2 was lower than expected 3"으로 막혔습니다.
   - 동기화 패스키(구글·애플)는 횟수를 늘 0으로 보내서 이 확인이 작동하지 않습니다.

## 등록 관련 추가 기록

### 서버에 저장된 값 = 공개키 (T08-C21·C22·C23)
배포 사이트 "학원" 계정의 패스키 "데탑"에 대해 서버(`me_passkeys.public_key`)가 가진 값입니다.

```
pQECAyYgASFYIOtgRScsGCIjditSRxV2PrNVmKpGg_sDmgi03mCw5X6HIlggeJIAyh6u4axFMBGbERV4-9j8oKMYg5g8xXfn-8zzcZI
```

- 이 값은 **공개키**(COSE_Key, base64url)이고 비밀번호가 아닙니다.
- 이 값으로는 서명을 만들 수 없어서, 누가 봐도 이것만으로는 들어올 수 없습니다. 그래서 화면에도 그대로 보여 줍니다.
- 등록 요청 본문에 실려 가는 것은 `attestationObject`, `clientDataJSON`, `publicKey`, `authenticatorData` 등이고, **개인키 칸은 없습니다.**
- 로컬 검증에서는 기기 안 개인키 값을 base64url·base64·hex 세 형태로 요청 본문에서 찾아봤고, 어디에도 없었습니다(`local-e2e.md` 카드 2).

### 등록을 취소하면 (T08-C25)
- 지문·PIN 확인을 취소하면 화면에 "등록을 취소했거나 시간이 지났습니다. 서버에는 아무것도 저장되지 않았습니다."가 뜹니다.
- 이때 `POST /api/register/verify` 요청 자체가 가지 않아서, 계정도 패스키도 생기지 않습니다(`local-e2e.md`).

### 패스키를 저장한 곳 (T08-C26)
| 계정 | 패스키 이름 | 저장한 곳 | 상태 |
|---|---|---|---|
| 학원 | 데탑 | **구글 비밀번호 관리자** (크롬) — 화면 표시 "동기화되는 패스키" | 사용 중 |
| 학원 | 학원 - 윈도우 헬로 | **Windows Hello** (기기 자체, 데스크톱) — 화면 표시 "이 기기 전용 패스키" | 삭제함 (기기 분실 재현) |
| 폰 | (아이폰에서 만든 패스키) | **iCloud 키체인** (아이폰 기기 자체, Apple 계정 동기화) | 사용 중 |

- 같은 Windows Hello에 두 번째를 만들려 하면 "이미 등록되어 있습니다"로 막혔습니다.
- 서버가 `excludeCredentials`로 이미 등록된 패스키를 기기에 알려 주기 때문입니다. 그래서 저장소가 다른 두 곳에 나눠 만들었습니다.

### 로그인 뒤 사람을 알아보는 방법 (T08-C32·C33)
- **세션 쿠키 방식**입니다. JWT처럼 정보를 담은 토큰을 브라우저가 들고 다니는 방식이 아닙니다.
- 쿠키에는 랜덤 값만 있고, 서버가 그 해시로 `me_sessions`에서 "어느 계정, 어느 패스키로 들어왔는지"를 찾습니다.
- 로그아웃하면 그 줄을 지웁니다. 그래서 로그아웃 전에 쓰던 쿠키 값을 그대로 붙여 다시 요청해도 **401**입니다(`local-e2e.md` 카드 3). 기록 속 세션 값은 앞 4자만 남기고 가렸습니다.
- 사이트 어디에도 비밀번호 입력 칸은 없습니다(T08-C35).

## 짧은 확인 방법
- **① 어디로 가나요**: 새 시크릿 창에서 https://readme-two-tau.vercel.app/ 을 엽니다.
- **② 세 단계 안에 무엇을 하나요**: (1) 소개 페이지가 그냥 보이는지 봅니다. (2) 맨 아래 점선 상자의 "나만의 자리 →"를 누릅니다. (3) 주소창에 https://readme-two-tau.vercel.app/api/private 를 직접 엽니다.
- **③ 무엇이 보이면 통과인가요**: 소개 내용이 보이고, `/me/`에는 "잠겨 있음"과 "패스키로 들어가기" 버튼만 있으며, `/api/private`는 `{"ok":false,"error":"로그인이 필요합니다."}`(401)입니다.
- **④ 안 될 때는 무엇이 보이나요**: "패스키로 들어가기"를 눌러도 이 사이트용 패스키가 없으니 창이 닫히고, 빨간 글씨로 "취소했거나 시간이 지났습니다"가 뜹니다. 이게 잠김이 정상인 모습입니다. 반대로 메모 내용이 보인다면 잠금이 실패한 것입니다.

## AI와 내 판단
- **AI에게 맡긴 일**: 패스키 등록·로그인·로그아웃·비공개 조회 API와 비공개 화면, 테이블 SQL, 자동 검증 스크립트를 작성하게 했습니다.
- **내가 직접 판단한 일**: 블루투스가 없는 환경에서 두 번째 패스키를 구글 비밀번호 관리자와 Windows Hello, 서로 다른 저장소에 나눠 만들었습니다. 꼬인 계정은 지우고 다시 만들었고, 실제 기기 두 대로 계정 두 개를 만들어 교차 확인했습니다.
- **AI 제안을 따르지 않은 일**: AI가 권한 가상 인증기·Bitwarden 확장 대신, 실제 백업이 되는 구글 비밀번호 관리자를 직접 찾아 두 번째 패스키로 썼습니다.
